# SQL · Урок 23. Проектирование БД (ER-диаграммы)

## Цели урока
- Читать и рисовать простые ER-диаграммы
- Определять сущности, атрибуты, связи
- Переходить от диаграммы к CREATE TABLE

## Теория

**ER (Entity-Relationship)**
- **Сущность (Entity)** — объект: User, Product, Order
- **Атрибут** — свойство: name, price, email
- **Связь (Relationship)** — как сущности связаны: 1:1, 1:N, M:N

**Кардинальность**
- 1 — один
- N (или *) — много
- 0..1 — ноль или один

**Пример: интернет-магазин**
```
[User] 1 ──── N [Order] N ──── N [Product]
                      │
                      └── через OrderItem (order_id, product_id, qty, price)
```

**От диаграммы к SQL**
1. Каждая сущность → таблица
2. Атрибуты → столбцы
3. 1:N → внешний ключ на стороне «многих»
4. M:N → промежуточная таблица
5. 1:1 → внешний ключ + UNIQUE

**Полезные вопросы при проектировании**
- Что мы храним?
- Какие запросы будут частыми?
- Что уникально идентифицирует запись?
- Что нельзя потерять при удалении (CASCADE / RESTRICT)?

**Инструменты**
- Бумага / draw.io / dbdiagram.io / Lucidchart
- DB Browser, DBeaver — визуализация существующей схемы

## Типичные ошибки
- Одна «большая» таблица на всё
- Забыть промежуточную таблицу для M:N
- Слабые имена (data1, value2)

## Практика
1. Нарисуйте (текстом) ER для блога: User, Post, Comment, Tag.
2. Укажите кардинальности.
3. Напишите CREATE TABLE для этой схемы.

## Проверь себя
1. Что такое сущность и связь?
2. Как реализуется M:N в таблицах?
3. Зачем рисовать ER до написания SQL?
